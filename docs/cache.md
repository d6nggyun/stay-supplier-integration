# 요금/재고 캐시

검색은 매 요청마다 공급사 재고·요금 API를 실시간 호출합니다. 반복되는 인기 질의(같은 날짜·인원)의 공급사 부하·지연을 줄이기 위해 청크 호출 결과를 짧게 캐시합니다. 캐시는 표시용(display-grade)이며, 예약 확정 시에는 신뢰하지 않고 실시간 재검증합니다(예약 흐름 도입 시).

## 1. 캐시 단위·키

**청크 단위**로 캐시합니다. 키는 `(supplier, 정렬된 코드 목록, 검색 조건)`입니다.

```
key = supplier | sort(codes) | checkIn | checkOut | adults | children
val = 그 청크의 SupplierSearchResult (offer 목록)
```

### 왜 청크 단위인가 (숙소 단위와 비교)

캐시 단위 후보는 **청크 단위** `(supplier, 코드집합, 조건)`와 **숙소 단위** `(supplier, 단일코드, 조건)` 둘입니다. 두 방식 모두 **조건(날짜·인원)을 키에 포함**하므로, 날짜가 하루만 바뀌어도 미스인 것은 **동일**합니다. 차이는 오직 **"코드 축"(숙소 목록이 바뀔 때의 대응)** 뿐입니다.

| 항목 | 청크 단위 | 숙소 단위 |
| --- | --- | --- |
| 숙소 목록 변경 시 | 코드집합이 바뀌어 **그 청크 통째 미스** | **바뀐 숙소만 미스**, 나머지 유지 |
| 구현 복잡도 | 호출 결과를 통째 저장 → **단순** | 미스 숙소만 배치 조회 → 숙소별 분해 → 병합 → **복잡** |
| single-flight 궁합 | **캐시 단위(키)=호출 단위(청크)**라 Caffeine의 키별 동시-미스 1회 로드가 곧 "청크당 호출 1회" | 키(숙소)≠호출 단위(배치)라 어긋남 — 미스 여러 숙소를 한 배치로 모으려면 bulk 로더로 별도 조율 필요 |
| 재사용 | 코드집합이 요청마다 동일해 같은 조건이면 히트 | 부분 겹침까지 재사용 → 더 세밀 |

**결정: 청크 단위.** 근거는 세 가지입니다.

1. **재사용** — 청크에 넣는 코드집합은 사용자 입력이 아니라 **활성 매핑에서 나오므로 요청마다 동일**합니다(누가 무엇을 검색하든 그 공급사의 코드집합은 같고, 카탈로그 동기화 때만 바뀜). 그래서 키에서 바뀌는 축은 사실상 조건(날짜·인원)뿐이라, 청크 단위로도 같은 조건 재검색이 잘 히트합니다.
2. **단순함** — "호출 결과(청크의 `SupplierSearchResult`)를 통째 저장"이라 캐시 레이어가 청크 호출을 감싸는 것으로 끝납니다.
3. **single-flight 궁합** — **캐시하는 단위(청크 키)와 공급사를 부르는 단위(청크)가 같아서**, Caffeine이 기본 제공하는 "같은 키의 동시 미스를 한 번만 로드"가 곧바로 "청크당 공급사 호출 1회"가 됩니다. 동시 미스가 나도 그 키 하나로 바로 처리됩니다.

   숙소 단위는 키(숙소 1개)와 호출 단위가 어긋납니다. 공급사 API가 배치(여러 코드를 한 번에)라 숙소마다 따로 부르는 건 비효율적이므로, **미스난 숙소들을 하나의 배치 호출로 묶고 → 돌아온 배치 응답을 다시 숙소별 캐시 항목으로 쪼개 나눠 담아야** 합니다. 이 "묶고 → 나누고 → 각 숙소 키의 future에 붙이는" 과정을 Caffeine의 키별 single-flight와 함께 맞추려면 bulk 로더(`getAll`)로 별도 조율이 필요합니다. 그래서 청크 단위처럼 "바로 쓰면 되는" 게 아니라 손이 더 갑니다.

청크 단위의 약점("목록이 하나만 바뀌어도 청크 통째 미스")은 **동기화 주기가 시간 단위로 드물고 캐시 TTL이 짧아** 실무 영향이 작습니다. 숙소 단위(부분 변경에 더 견고)는 위 복잡도 때문에, **숙소가 많아지고 목록 변경이 잦아지는 규모 확장 시의 다음 단계**로 둡니다.

### 키·값 선택 근거

**키에는 "응답을 결정하는 모든 입력"을 넣습니다.** 하나라도 빠지면 서로 다른 입력인데 같은 캐시값을 주게 되어 틀립니다.

- `supplier`: 공급사마다 데이터·코드 체계가 독립이라 반드시 분리합니다.
- `codes`(정렬): 값이 "바로 그 코드들의 offer"라, 코드 집합이 다르면 결과가 다릅니다. `findAll` 순서가 보장되지 않으므로 **정렬**해 같은 집합이 항상 같은 키가 되게 합니다.
- `checkIn·checkOut·adults·children`: 재고·요금이 날짜·인원에 따라 달라지는 질의 파라미터라 키에 포함합니다.

**값은 원본 HTTP 바디가 아니라 표준 모델로 정규화한 `SupplierSearchResult`(offer 목록)입니다.** 그래서 히트 시 **호출뿐 아니라 파싱·정규화까지 건너뜁니다.** 내부 식별자 치환 이전 단계라, 치환은 히트해도 매번 최신 매핑으로 수행됩니다.

### 참고

- 코드 목록은 사용자 입력이 아니라 **활성 매핑**에서 나오므로 요청 간에는 동일하고, 동기화(주기: 시간 단위)로만 바뀝니다. 캐시 TTL(짧음)이 동기화 주기보다 훨씬 짧아, 캐시 유효 구간에서는 코드 목록이 안정적입니다.
- 키에서 실제로 다양하게 바뀌는 축은 **검색 조건(날짜·인원)**입니다. 그래서 캐시는 "모든 날짜를 덮는" 게 아니라 **반복되는 인기 질의를 덮는** 구조입니다.

## 2. 위치 — 리질리언스보다 바깥

캐시는 청크 호출의 **가장 바깥**에 둡니다. 히트면 타임아웃·재시도·서킷·공급사 호출을 **전부 건너뜁니다.**

```
callChunk:
  cache.get(key, loader = ( adapter.search().timeout().retry().circuitBreaker() ))
    → 히트: 캐시값 반환(호출 없음)
    → 미스: loader 실행(리질리언스 경유), 성공 결과만 캐시
  .map(success).onErrorResume(→ 상태로 흡수)
```

**성공 결과만 캐시**합니다. 실패·타임아웃·서킷 차단은 캐시하지 않아, 다음 요청에서 다시 시도되게 합니다(Caffeine은 실패한 future를 캐시에 남기지 않음).

## 3. 스탬피드(thundering herd) 방지

- **Single-flight**: 같은 키의 동시 미스는 **한 번만** 공급사를 호출하고 나머지는 그 로드를 공유합니다. Caffeine `AsyncCache`가 키 단위로 자동 처리합니다.
- **TTL 지터**: 각 엔트리 TTL에 무작위 오프셋을 더해 동시 만료로 인한 몰림을 분산합니다(`ttl ± random(jitter)`).

### 만료는 "가져온 시점" 기준(expireAfterWrite), 읽기로 연장하지 않음

읽을 때마다 TTL을 연장(expireAfterAccess)하지 **않습니다.** 요금·재고는 변동 데이터라, 읽기로 연장하면 **인기 질의일수록 같은 stale 값을 계속 서빙하며 절대 갱신되지 않는** 문제가 생깁니다(가장 인기 있는 질의가 가장 오래된 데이터가 됨).

여기서 **TTL은 "가격·재고의 최대 stale 허용치"** 이므로, **읽은 시각이 아니라 가져온 시각** 기준이어야 의미가 있습니다. expireAfterWrite로 두면 인기 질의도 TTL마다 재조회되어 **stale 상한이 TTL로 보장**됩니다. (읽기 연장은 설정·참조 데이터처럼 신선도가 중요하지 않은 캐시에 적합합니다.)

## 4. 저장 위치·라이브러리

- **Caffeine(인프로세스) `AsyncCache`**: 앱 메모리 안의 고성능 캐시. 네트워크 홉이 없고 single-flight·크기/시간 축출을 내장합니다.
- 다중 인스턴스에서 캐시 공유가 필요해지면 **Redis로 승격**하는 경로를 둡니다(현재는 단일 인스턴스 전제).

## 5. 설정 (`supplier.cache.*`)

```yaml
supplier:
  cache:
    enabled: true
    ttl-ms: 30000        # 표시용 신선도 기준. 잠정값이며 운영에서 튜닝한다.
    jitter-ms: 5000      # 동시 만료 분산용 무작위 오프셋 상한
    maximum-size: 10000  # 엔트리 상한(초과 시 축출)
```

TTL은 **요금·재고의 변동 속도 + 허용 stale(예약 재검증이 완화) + 관측 히트율**로 정하는 튜닝 영역입니다. 예약 확정에서 실시간 재검증하므로 표시용 stale은 그 안전망 안에서 허용합니다. 재고가 적은 상품에 더 짧은 TTL을 주는 적응형 TTL은 향후 여지로 둡니다.
