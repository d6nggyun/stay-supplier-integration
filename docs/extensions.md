# 확장 설계 (미구현)

아래는 필수 범위를 안정화한 뒤 검토하는 확장들의 **설계 초안**입니다. 현재 코드에는 구현되어 있지 않으며, 방향·판단·저장소 반영 시 변경점을 남깁니다. 각 항목은 이후 개별 문서·구현으로 승격될 수 있습니다.

각 확장의 공통 원칙은 두 가지입니다. **(1) 원본 데이터는 절대 잃지 않는다** (캐시·환산·병합은 원본 위의 파생일 뿐). **(2) 표시(display)와 확정(booking)을 분리한다** (표시는 근사·지연 허용, 확정은 항상 실시간 원본으로 재검증).

---

## 1. 요금/재고 캐시 전략

### 문제

검색은 매 요청마다 공급사 재고·요금 API를 실시간 호출합니다. 캐시는 공급사 부하·지연을 줄이지만, 요금·재고는 자주 바뀌어 **stale(오래된) 값**을 보여줄 위험이 있습니다.

### 무엇을 캐시하나

- **숙소 목록(카탈로그)**: 이미 매핑 DB가 사실상 캐시 역할을 합니다(주기 동기화). 추가 캐시 불필요.
- **재고·요금 응답**: 변동이 잦은 부분. 캐시 키는 `(supplier, stayCode, checkIn, checkOut, adults, children)`. 조건 조합이 많아 **키 카디널리티가 높음**에 유의합니다.

### TTL·정합성 오차 허용

- 재고·요금 TTL은 **짧게**(예: 30~60초). 길수록 오판매(overselling)·잘못된 가격 위험이 커집니다.
- **표시 지연은 TTL 내에서 허용**하되, **예약 확정 단계에서는 캐시를 신뢰하지 않고 실시간 재검증**합니다(§5와 연결). 즉 "목록은 근사, 결제 직전은 정확".
- 재고가 0에 가까운 상품은 TTL을 더 짧게(또는 캐시 제외)하는 적응형 TTL도 고려 대상입니다.

### 캐시 스탬피드(thundering herd) 방지

인기 키의 TTL이 만료되는 순간, 동시 요청들이 한꺼번에 미스 → 공급사로 몰리는 문제입니다.

- **Single-flight(요청 병합)**: 같은 키의 동시 미스는 **한 번만** 공급사를 호출하고 나머지는 그 결과를 공유. (Caffeine `AsyncLoadingCache`가 키별 계산 중복 제거를 제공)
- **TTL 지터(jitter)**: 만료 시각에 무작위 오프셋을 더해 대량 동시 만료를 분산.
- **Stale-while-revalidate**: 만료돼도 짧게 stale 값을 내보내고 백그라운드로 갱신.

### 저장 위치

- 단일 인스턴스: **Caffeine(인프로세스)**. 가장 단순.
- 수평 확장(다중 인스턴스): **Redis(공유 캐시)**. 인스턴스 간 일관성·부하 절감이 크지만 인프라가 추가됩니다.
- 방침: Caffeine으로 시작하고, 다중 인스턴스가 되면 Redis로 승격하는 경로를 둡니다.

### 방침 정리

재고·요금 응답을 짧은 TTL + single-flight + 지터로 캐시하고, 예약 확정은 항상 실시간 재검증. 부정 캐시(negative cache)는 아주 짧게만(에러를 오래 캐시하지 않음).

### 저장소 반영 시 변경점

- 어댑터 `search()` 앞단에 캐시 조회/적재 레이어(캐시 키·로더). `spring-boot-starter-cache` + Caffeine 또는 Redis.
- 캐시 히트율·미스·로드 지연 지표 추가(observability와 연결).

## 2. 정규화 실패 데이터 격리

### 문제

현재 정규화할 수 없는 항목(매핑 없는 코드, 역직렬화·형식 오류)은 결과에서 **스킵하고 경고 로그만** 남깁니다([supplier-adapter.md](supplier-adapter.md) §4). 확장은 이를 **버리지 않고 격리·기록**해 추후 분석 가능하게 합니다(dead-letter).

### 설계

- **무엇을**: 실패한 원본 조각(raw payload) + 사유 코드 + 공급사 + 발생 시각 + 요청 맥락(검색 조건)을 격리 저장.
- **어디서**: 정규화·치환 지점(어댑터 `toOffer` 또는 오케스트레이터 `toStayOffers`)에서 실패 시 스킵 대신 격리 레코드를 남김.
- **저장소**: 조회·집계가 필요하므로 DB 테이블(`normalization_failure`) 권장. 대량이면 로그 스트림 + 수집기(예: 로그 집계)도 대안.
- **최우선 원칙 — 검색을 막지 않음**: 격리 기록은 **best-effort**로, 기록 자체가 실패해도 검색 결과(부분 성공)에는 영향이 없어야 합니다.
- **사유 코드**: `MAPPING_NOT_FOUND`, `DECODE_ERROR`, `MISSING_FIELD` 등으로 분류해 재발 패턴을 분석.
- **보존·민감정보**: 원본에 민감정보가 있을 수 있어 보존 기간·마스킹 정책 필요.

### 방침 정리

정규화 불가 항목을 사유 코드와 함께 dead-letter로 격리(best-effort), 검색은 그대로 부분 성공 반환. 축적된 실패를 분석해 매핑·어댑터를 개선.

### 저장소 반영 시 변경점

- `infrastructure.persistence`에 격리 엔티티·리포지토리, 격리를 담당하는 컴포넌트(예: `NormalizationFailureRecorder`).
- `toStayOffers`의 "스킵 + warn"을 "격리 기록 + 스킵"으로 교체. 격리 건수 지표 추가.

## 3. 중복 상품 병합

### 문제

A·B가 **같은 물리적 숙소**를 각자의 코드로 팔 수 있습니다. 현재는 각각 별도 상품(별도 내부 식별자)으로 노출합니다. 확장은 이를 하나로 합칠지(그룹핑) 판단·구현합니다.

### 어려운 지점

공급사 간 **공통 키가 없습니다.** 이름·주소·좌표로 추정 매칭해야 하는데, 잘못 합치면(false merge) **다른 숙소의 가격·정보를 한 상품으로** 보여주는 심각한 오류가 됩니다.

### 선택지

| 방식 | 장점 | 위험 |
| --- | --- | --- |
| (a) 분리 유지(현재) | 오병합 없음, 단순 | 같은 숙소가 중복 노출 |
| (b) 자동 퍼지 매칭(이름 정규화+좌표 근접) | 자동·확장적 | 오병합 위험이 서빙 경로에 직접 노출 |
| (c) 큐레이션 매핑(운영이 "동일 숙소" 매핑 관리) | 정확 | 수작업 비용 |

### 설계

- **정본 숙소(canonical property) 개념 도입**: 여러 `(supplier, stayCode)`를 하나의 정본 id로 묶는 그룹 매핑.
- 그룹 채우기는 **(c) 큐레이션을 우선**, **(b) 퍼지 매칭은 "후보 제안"**으로만 두고 사람이 검토해 승격(서빙 경로에서 자동 병합하지 않음 → 오병합·오판매 방지).
- **병합 표시 정책**: 정본 이름·메타데이터를 대표로, 비교 가능한 객실 타입 단위로 **최저가 선택**. 객실 타입 매칭도 퍼지하므로 신중히(불확실하면 병합하지 않고 분리 유지).

### 방침 정리

정본 그룹핑 모델을 두되 기본은 분리 노출, 그룹이 확정된 경우에만 병합. 서빙 경로의 자동 퍼지 병합은 지양.

### 저장소 반영 시 변경점

- `property_group`(정본 id) ↔ `(supplier, stayCode)` 매핑 테이블. 검색 결과를 정본 id로 그룹핑·중복 제거하는 후처리 단계.
- 퍼지 후보 산출·검토 도구는 별도(운영 기능, 범위 밖).

## 4. 통화(currency) 처리

### 문제

현재는 환산 없이 공급사가 준 ISO 4217 코드를 그대로 노출합니다. 서로 다른 통화의 상품을 **함께 비교·정렬**하려면 환산이 필요합니다.

### 설계

- **원본 보존**: 통화 코드 + 금액(원본)을 항상 진실의 출처로 유지합니다. 환산은 그 위의 파생.
- **표시 환산(display conversion)**: 요청/사용자 표시 통화로 환산한 근사값을 **부가 제공**하고 "약(approximate)"·**환율 기준 시각**을 함께 표기.
- **확정은 원본 통화로**: 결제·예약은 절대 환산값이 아니라 공급사 원본 통화로 처리(§5).
- **환율 소스**: 환율 제공자 + 캐시(TTL). 소스 장애 시 환산 생략하고 원본만 노출(우아한 degrade).
- **통화별 반올림**: 소수 단위가 다름(JPY·KRW 0자리, USD 2자리). 통화별 규칙 적용.
- **정렬·비교**: 표시 통화 기준으로 수행하되, 환산 불가 상품은 뒤로 두거나 별도 표기.

### 방침 정리

이중 표현(원본=권위, 표시 환산=근사·환율시각 표기), 비교·정렬은 표시 통화로, 확정은 원본 통화로.

### 저장소 반영 시 변경점

- 도메인 `Price`에 표시 환산값을 얹는 파생 계층(원본 record는 불변 유지). 환율 조회 포트 + 캐시. 응답 DTO에 표시 통화·환율 시각 필드 추가.

## 5. 예약 대행 흐름

### 문제

공급사에 예약을 **생성·취소**하는 흐름과, 중간 실패 시 **보상(compensation)** 처리. 현재 어댑터는 검색만 있고 예약 개념이 없습니다.

### 흐름 (saga)

1. 고객이 offer 선택(supplier, stayCode, roomType, 날짜, 가격).
2. **재검증**: 캐시를 신뢰하지 않고 실시간 재고·요금 확인(§1과 연결). 가격·재고가 바뀌었으면 중단·재확인.
3. **예약 생성**: 공급사 예약(hold/confirm) 호출.
4. 로컬 예약 레코드 저장(상태 기계: `PENDING → CONFIRMED`).
5. 임의 단계 실패 시 **보상**: 이미 만든 공급사 예약이 있으면 취소, 로컬은 `FAILED`.

### 핵심 판단

- **멱등성(idempotency)**: 예약 생성은 클라이언트 생성 idempotency key로 **재시도해도 중복 예약이 안 되게** 함. 타임아웃으로 "생성됐는지 모름" 상태가 가장 위험.
- **모호한 타임아웃 처리(reconciliation)**: 생성 응답을 못 받은 경우, idempotency key로 공급사에 조회하거나 취소해 정합을 맞추는 보정 잡.
- **보상 트랜잭션**: 분산 트랜잭션 대신 saga(오케스트레이션) + 보상 액션(예약 취소). saga 상태를 저장.
- **취소 흐름**: 로컬 취소 → 공급사 취소 API → 상태 갱신. 공급사 취소 실패 시 재시도·수동 개입 경로.

### 방침 정리

saga 오케스트레이션 + 멱등 키 + 로컬 예약 상태 기계(`PENDING/CONFIRMED/CANCELLED/FAILED`), 실패 시 공급사 예약 취소로 보상, 모호한 타임아웃은 보정 잡으로 정합. 규모가 커서 이 항목은 **설계 우선**(간단 구현 시 생성/취소 + 보상만 최소로).

### 저장소 반영 시 변경점

- 어댑터 포트에 `createBooking`·`cancelBooking` 추가, 공급사별 구현. 예약 도메인·상태 기계·영속, saga 오케스트레이터, 멱등 키 저장. 검색과 별개의 큰 하위 시스템이라 단계적 도입.

## 우선순위 메모

구현 여력이 생기면 **효과 대비 비용**을 기준으로 봅니다. 캐시(1)·정규화 실패 격리(2)는 기존 검색 경로에 얹기 쉬워 우선 후보이고, 통화(4)는 표시 계층 확장이라 중간, 중복 병합(3)·예약 대행(5)은 새 하위 시스템·오병합/정합 리스크가 커 설계를 더 다진 뒤 진행합니다.
