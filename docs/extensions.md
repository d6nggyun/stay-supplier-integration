# 확장 설계

아래는 필수 범위를 안정화한 뒤 검토하는 확장들의 **설계 초안·의사결정**입니다. 방향·판단·저장소 반영 시 변경점을 남깁니다. 이 중 요금/재고 캐시(§1, [cache.md](cache.md))와 정규화 실패 격리(§2, [supplier-adapter.md](supplier-adapter.md) §4)는 구현됐고, 재시도·서킷([resilience.md](resilience.md))·연동 지표([observability.md](observability.md))도 구현됐습니다. 중복 병합(§3)은 **자동 병합하지 않기로 결정**(분리 노출 유지)했고, 통화(§4)·예약 대행(§5)은 아직 설계 초안입니다.

각 확장의 공통 원칙은 두 가지입니다. **(1) 원본 데이터는 절대 잃지 않는다** (캐시·환산·병합은 원본 위의 파생일 뿐). **(2) 표시(display)와 확정(booking)을 분리한다** (표시는 근사·지연 허용, 확정은 항상 실시간 원본으로 재검증).

---

## 1. 요금/재고 캐시 전략 — 구현됨

청크 단위 캐시(Caffeine `AsyncCache`, single-flight + TTL 지터, 성공만 캐시, 예약 확정 시 재검증)로 구현했습니다. 확정 설계와 설정은 [cache.md](cache.md)를 참고하세요.

## 2. 정규화 실패 데이터 격리 — 구현됨

정규화할 수 없어 제외된 항목을 버리지 않고 `normalization_failure` 테이블에 사유(`MAPPING_NOT_FOUND`)와 함께 best-effort로 격리합니다. 상세는 [supplier-adapter.md](supplier-adapter.md) §4를 참고하세요.

## 3. 중복 상품 병합 — 결정: 자동 병합하지 않음(분리 노출 유지)

### 문제

A·B가 **같은 물리적 숙소**를 각자의 코드로 팔 수 있습니다(예: A `hotelCode`, B `propertyId`). 현재는 각각 별도 상품(별도 내부 식별자)으로 노출합니다. 이를 하나로 합칠지 판단합니다.

### 왜 자동 병합을 하지 않기로 했나

공급사 간 **공통 키가 없어**, 병합하려면 이름·주소·좌표로 **추정 매칭**해야 합니다. 그런데 서빙 경로에서 자동 매칭은 리스크가 큽니다.

- **오병합(거짓 양성)이 치명적**: 서로 **다른 물리적 호텔이 같은 이름**을 쓰는 경우가 반드시 존재합니다(체인·일반명, 예: 지점이 여럿인 "○○ Inn"). 이를 병합하면 **다른 호텔의 가격·재고를 한 상품으로** 보여주어 고객에게 심각한 혼동을 줍니다. 정확 이름 일치(byte-match)로 좁혀도 체인·일반명의 오병합은 남습니다.
- **이름만으로는 재현율도 낮음(거짓 음성)**: 같은 호텔도 공급사 간 표기가 달라("Riverside Hotel Seoul" vs "Riverside Hotel, Seoul" vs 한글명) 정확 일치로는 대부분 못 잡습니다. 정규화로 재현율을 올리면 거짓 양성이 함께 늘어납니다.
- **판별 데이터 부족**: 오병합을 걸러낼 **주소·좌표**가 현재 모델에 없습니다(이름만 있음). 그래서 안전한 자동 매칭 자체가 성립하기 어렵습니다.

즉 자동 병합의 **이득(중복 노출 제거)보다 오병합으로 인한 혼동 리스크가 크다**고 판단했습니다.

### 결정

- **분리 노출을 유지합니다**(현재 동작). 공급사별 상품을 그대로 각각 노출하고, 백엔드는 추정 병합을 하지 않습니다.
- 병합이 필요하다면 **오직 권위 있는 큐레이션 정본 매핑**(운영이 검증한 "동일 숙소" 매핑)으로만 합니다. 이름·퍼지 매칭은 큐레이션의 **후보 제안**으로만 쓰고, 서빙 경로에서 자동 적용하지 않습니다.
- 이 큐레이션 정본은 운영 도구·주소/좌표 등 **추가 데이터·인력이 필요해 이번 범위 밖**으로 둡니다. 데이터 없는 태깅 필드를 미리 넣지 않습니다("안 쓰는 코드 안 남김").

### 큐레이션 정본이 갖춰졌을 때의 표시 정책(향후)

정본 매핑이 생기면, 병합을 어떻게 **드러낼지**는 표시 계층 정책입니다.

- **(a) 태깅**: 결과에 `canonicalPropertyId`를 실어 같은 호텔임을 표시하고, 묶어 보이는 것은 소비자(프론트) 정책에 맡김. 비파괴적.
- **(b) 그룹 응답**: 정본 숙소 단위로 묶어 한 호텔 아래 공급사별 offer를 나열(응답 구조 재편).
- 어느 쪽이든 **객실 타입까지 공급사 간 병합하지 않습니다**("Deluxe Twin" vs "Deluxe Twin Room" 동일성 판정은 또 다른 퍼지 문제) — 숙소 단위 그룹핑까지만.

### 저장소 반영 시 변경점(향후 큐레이션 도입 시)

- `property_group`(정본 id) ↔ `(supplier, stayCode)` 매핑 테이블. 검색 결과에 정본 id를 태깅(a) 또는 그룹핑(b)하는 후처리.
- 퍼지 후보 산출·검토 도구는 별도(운영 기능, 범위 밖).

## 4. 통화(currency) 처리

### 문제

현재는 환산 없이 공급사가 준 ISO 4217 코드를 그대로 노출합니다. 서로 다른 통화의 상품을 **함께 비교·정렬**하려면 환산이 필요합니다.

### 설계

- **원본 보존**: 통화 코드 + 금액(원본)을 항상 진실의 출처로 유지합니다. 환산은 그 위의 파생.
- **표시 환산(display conversion)**: 요청/사용자 표시 통화로 환산한 근사값을 **부가 제공**하고 "약(approximate)"·**환율 기준 시각**을 함께 표기.
- **확정은 원본 통화로**: 결제·예약은 절대 환산값이 아니라 공급사 원본 통화로 처리(§5).
- **환율 소스**: 환율 제공자 + 캐시(TTL). 소스 장애 시 환산 생략하고 원본만 노출(우아한 degrade).
- **통화별 반올림**: 소수 단위가 다름(JPY·KRW 0자리, USD 2자리). 통화별 규칙 적용.
- **정렬·비교**: 표시 통화 기준으로 수행하되, 환산 불가 상품은 뒤로 두거나 별도 표기.

### 방침 정리

이중 표현(원본=권위, 표시 환산=근사·환율시각 표기), 비교·정렬은 표시 통화로, 확정은 원본 통화로.

### 저장소 반영 시 변경점

- 도메인 `Price`에 표시 환산값을 얹는 파생 계층(원본 record는 불변 유지). 환율 조회 포트 + 캐시. 응답 DTO에 표시 통화·환율 시각 필드 추가.

## 5. 예약 대행 흐름

### 문제

공급사에 예약을 **생성·취소**하는 흐름과, 중간 실패 시 **보상(compensation)** 처리. 현재 어댑터는 검색만 있고 예약 개념이 없습니다.

### 흐름 (saga)

1. 고객이 offer 선택(supplier, stayCode, roomType, 날짜, 가격).
2. **재검증**: 캐시를 신뢰하지 않고 실시간 재고·요금 확인(§1과 연결). 가격·재고가 바뀌었으면 중단·재확인.
3. **예약 생성**: 공급사 예약(hold/confirm) 호출.
4. 로컬 예약 레코드 저장(상태 기계: `PENDING → CONFIRMED`).
5. 임의 단계 실패 시 **보상**: 이미 만든 공급사 예약이 있으면 취소, 로컬은 `FAILED`.

### 핵심 판단

- **멱등성(idempotency)**: 예약 생성은 클라이언트 생성 idempotency key로 **재시도해도 중복 예약이 안 되게** 함. 타임아웃으로 "생성됐는지 모름" 상태가 가장 위험.
- **모호한 타임아웃 처리(reconciliation)**: 생성 응답을 못 받은 경우, idempotency key로 공급사에 조회하거나 취소해 정합을 맞추는 보정 잡.
- **보상 트랜잭션**: 분산 트랜잭션 대신 saga(오케스트레이션) + 보상 액션(예약 취소). saga 상태를 저장.
- **취소 흐름**: 로컬 취소 → 공급사 취소 API → 상태 갱신. 공급사 취소 실패 시 재시도·수동 개입 경로.

### 방침 정리

saga 오케스트레이션 + 멱등 키 + 로컬 예약 상태 기계(`PENDING/CONFIRMED/CANCELLED/FAILED`), 실패 시 공급사 예약 취소로 보상, 모호한 타임아웃은 보정 잡으로 정합. 규모가 커서 이 항목은 **설계 우선**(간단 구현 시 생성/취소 + 보상만 최소로).

### 저장소 반영 시 변경점

- 어댑터 포트에 `createBooking`·`cancelBooking` 추가, 공급사별 구현. 예약 도메인·상태 기계·영속, saga 오케스트레이터, 멱등 키 저장. 검색과 별개의 큰 하위 시스템이라 단계적 도입.

---

## 우선순위 메모

구현 여력이 생기면 **효과 대비 비용**을 기준으로 봅니다. 기존 검색 경로에 얹기 쉬운 캐시(1)·정규화 실패 격리(2)를 먼저 구현했습니다. 중복 병합(3)은 오병합 리스크가 커 **자동 병합하지 않기로 결정**하고 큐레이션 정본을 향후로 뒀습니다. 통화(4)는 표시 계층 확장, 예약 대행(5)은 새 하위 시스템이라 설계를 더 다진 뒤 진행합니다.
