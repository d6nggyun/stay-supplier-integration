# 통합 검색 흐름

## 1. 처리 순서

1. 고객의 검색 조건 검증
2. DB에서 활성(`active = true`) 숙소 매핑 조회
3. 공급사별로 숙소 코드 그룹화
4. 공급사별 숙소 코드를 최대 50개 단위로 분할
5. Supplier A와 Supplier B를 병렬 호출
6. 각 응답을 표준 모델로 정규화
7. 재고와 요금 계산
8. 공급사 코드를 내부 식별자로 매핑
9. 결과와 공급사별 상태를 합쳐 응답

## 2. 병렬 호출

공급사 호출은 `WebClient`와 `Mono`·`Flux`로 병렬 처리합니다. 개념적으로 다음 구조를 사용합니다.

```
Flux.merge(
    searchSupplierA(criteria),
    searchSupplierB(criteria)
)
```

각 공급사 호출은 서로 독립적이어야 합니다. 한 공급사가 실패하더라도 다른 공급사의 결과가 취소되거나 사라지면 안 됩니다.

리액티브 경계는 애플리케이션 서비스 내부로 한정합니다. 병렬 조합은 `Mono`·`Flux`로 처리하되 서비스 끝에서 결과를 블로킹으로 받아, 컨트롤러는 동기 방식으로 반환합니다. (실행 모델의 근거는 [architecture.md](architecture.md) 참고)

## 3. 50개 초과 처리 (청크 분할)

재고·요금 API는 한 번에 최대 50개 숙소 코드를 받습니다. 초과하면 청크 단위로 분할합니다.

```
숙소 코드 120개
→ 50개
→ 50개
→ 20개
```

청크 호출에는 동시성 상한(`supplier.search.chunk-concurrency`)을 둡니다. 무제한 병렬 호출은 공급사의 Rate Limit(429)을 초과할 수 있기 때문입니다. 분할 크기는 `supplier.search.chunk-size`(규약상 최대 50)로 둡니다.

예시 데이터는 50개 미만이라 실제로는 단일 청크로 흐르지만, 오케스트레이터는 코드를 `chunk-size` 단위로 나눠 `chunk-concurrency` 상한으로 호출하도록 구현되어 규모가 커져도 그대로 동작합니다. 일부 청크만 실패하면 성공 청크 결과를 유지한 채 `PARTIAL_SUCCESS`로 표기합니다.

### 규모 확장에 대한 메모

청크 분할만으로는 수천 개 규모를 감당할 수 없습니다. 공급사당 호출 수가 선형으로 늘어 Rate Limit에 걸리므로, 전체 조회 대신 대상을 좁힐 조건과 캐시가 함께 필요합니다. 이 부분은 확장 범위로 두고 방향만 남깁니다.

## 4. 타임아웃

타임아웃은 두 층위로 나눕니다. **개별 호출 타임아웃**과 **전체 요청 예산**입니다.

### 개별 호출 타임아웃 (잠정값)

```
Connection timeout: 1초   (supplier.search.connect-timeout-ms)
Response timeout: 3초      (supplier.search.response-timeout-ms)
```

- 연결 타임아웃은 공급사 서버에 연결할 수 없는 상황을 빠르게 종료하기 위한 값입니다. **커넥터(전송 계층)에 설정**합니다.
- 응답 타임아웃은 연결 이후 응답이 오지 않는 상황에서 고객 요청이 계속 대기하지 않도록 하기 위한 값입니다. **오케스트레이터가 청크 호출 하나당 `.timeout()`으로 적용**합니다.
- 두 타임아웃 모두 공급사별 상태로는 `TIMEOUT`으로 통일합니다.

### 전체 요청 예산

개별 호출 타임아웃만 두면, 청크가 여러 개로 나뉘고 동시성 상한에 걸릴 때(예: 3청크·동시성 2 → 최대 2라운드) 고객 체감 지연이 개별 응답 타임아웃을 넘길 수 있습니다.

따라서 검색 요청 전체에 상한(`supplier.search.request-budget-ms`, 잠정 6초)을 별도로 둡니다. **공급사별 파이프라인에 예산을 적용하며, 공급사 호출은 병렬이라 벽시계 지연은 예산에 수렴합니다.** 예산을 초과한 공급사는 `TIMEOUT`으로 마감하고, 그때까지 완료된 다른 공급사 결과로 응답합니다.

예시 데이터는 50개 미만 단일 청크라 전체 예산에 도달하지 않지만, 청크가 늘어나는 확장 상황에서도 고객 대기 시간이 무한정 늘어나지 않도록 상한을 명시합니다.

실제 값은 Mock 공급사의 무응답 시나리오로 검증하고 구현 과정에서 조정합니다.

## 5. 오케스트레이터 구현 시 확정한 사항

- **조회 트랜잭션 경계**: 활성 매핑은 공급사 호출 **전에** 한 번에 읽어 조회용 맵(코드 → 내부 식별자)으로 만들고, 이후 네트워크 호출은 트랜잭션 밖에서 수행합니다. 느린 외부 호출이 DB 커넥션·트랜잭션을 붙잡지 않게 하기 위함입니다.
- **결과 정렬**: 병렬 호출 결과는 완료 순서로 섞여 도착하므로, 최종 결과는 공급사 순서로 정렬해 응답을 안정화합니다.
- **내부 식별자 치환 실패**: 응답 offer의 공급사 코드에 대응하는 내부 식별자가 없으면(로딩 이후 매핑 소멸 등) 코드를 노출하는 대신 해당 offer를 제외하고 경고 로그를 남깁니다. (정규화 실패 격리 방침은 [supplier-adapter.md](supplier-adapter.md) 참고)
