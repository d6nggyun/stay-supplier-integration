# 공급사 코드와 내부 식별자 매핑

## 1. 매핑이 필요한 이유

공급사의 재고·요금 API는 지역으로 검색해 주지 않고, 숙소 코드 목록을 받아야만 응답합니다. 따라서 어떤 숙소를 조회할지 우리가 먼저 알고 있어야 합니다.

숙소 목록 API는 조건 없이 전체 목록만 제공하며 정적이고 변동이 적습니다. 반면 재고·요금 API는 매번 값이 달라집니다. 이 성격 차이 때문에 숙소 목록으로 확보한 코드를 매핑으로 저장해 두고, 검색 시점에는 저장된 코드로 재고·요금 API를 호출합니다.

## 2. 매핑 키

### 숙소 매핑

논리적 키는 `(supplier, supplierStayCode)`입니다.

```
(SUPPLIER_A, A-10023)
(SUPPLIER_B, B77120)
```

같은 공급사 코드가 다시 조회되면 기존 내부 숙소 식별자를 재사용합니다.

### 객실 타입 매핑

객실 타입 코드는 숙소 내부에서만 유일합니다. 따라서 논리적 키는 세 값으로 구성합니다.

```
(supplier, supplierStayCode, supplierRoomTypeCode)
```

```
(SUPPLIER_A, A-10023, DLX-TWN)
(SUPPLIER_B, B77120, R-401)
```

객실 타입 코드만 저장하면 서로 다른 숙소에서 같은 객실 코드가 사용될 때 충돌할 수 있습니다.

## 3. 내부 식별자 생성

내부 식별자는 DB가 자동 생성하는 숫자 식별자(`IDENTITY` 전략)를 사용합니다.

- 숙소 매핑이 새로 생성될 때 내부 숙소 ID를 발급합니다.
- 객실 타입 매핑이 새로 생성될 때 내부 객실 타입 ID를 발급합니다.
- 기존 공급사 코드가 존재하면 기존 내부 ID를 재사용합니다.
- `(supplier, supplierCode)`에 유니크 제약을 설정합니다.
- 저장은 애플리케이션 레벨 upsert로 처리합니다. 즉 유니크 키로 조회한 뒤 없으면 삽입, 있으면 갱신하며, 동시 실행 시의 경합은 유니크 제약으로 방어합니다. (H2/JPA에서는 DB MERGE가 아니라 조회 후 저장 방식입니다.)

공급사 코드 문자열을 내부 ID로 그대로 쓰지 않는 이유는, 외부 코드와 내부 식별자를 분리하기 위해서입니다. 결정적 해시도 검토했으나 충돌 처리 코드만 늘고, 공급사 코드를 조합한 문자열은 "공급사 코드가 아닌 자사 식별자"라는 요구와 어긋나 제외했습니다.

내부 식별자는 별도의 대리 키를 두지 않고 테이블의 PK로 둡니다. 현재는 병합(확장 범위)이 없어 매핑 행과 내부 식별자가 1:1이기 때문입니다. 병합을 구현하면 여러 매핑 행이 같은 내부 식별자를 공유해야 하므로, 그때 대리 PK(`id`)를 분리하고 내부 식별자는 일반 컬럼으로 내립니다.

### 식별자 생성 전략과 규모 확장

식별자 생성 전략은 현재 `IDENTITY`(DB 자동 증가)입니다. 저장 대상이 매핑 2개 테이블이고 쓰기가 병목이 아니어서, 예측 가능한 순차 id와 DB 이식성(H2·MySQL 공통)을 우선했습니다.

매핑 쓰기가 대량·고빈도가 되어 병목이 되면 `SEQUENCE` + JDBC 배치 삽입으로 전환하는 확장 경로가 있습니다. `IDENTITY`는 생성 키를 INSERT 시점에 받아 배치 삽입을 막지만, `SEQUENCE`는 id를 미리 받아 여러 INSERT를 묶어 DB 왕복을 줄입니다. 전환 시에는 `hibernate.jdbc.batch_size`·`order_inserts`·`allocationSize`를 함께 맞추고, `allocationSize`를 올릴 때 생기는 id 구멍(gap)과 DB 시퀀스 증가폭 정합성을 검증해야 합니다. 또한 `SEQUENCE`는 MySQL 같은 네이티브 시퀀스 미지원 DB에서는 재검토가 필요합니다. 현재 규모에서는 이 이득이 측정되지 않아 도입하지 않고 설계로만 남깁니다.

두 공급사가 실제로 같은 숙소를 제공하더라도 공통 키가 없으므로 각각 별도의 내부 상품으로 관리합니다. 이름을 이용한 자동 병합은 오병합 위험이 있어 이번 구현에서는 후순위로 두고 확장 범위로 남깁니다. 이 항목에서 필수는 "같은 공급사 상품이 항상 같은 내부 식별자로 돌아오는 것"이지, 서로 다른 공급사의 상품을 같은 식별자로 묶는 것이 아닙니다.

## 4. 테이블

### `stay_mapping`

```
- internal_stay_id (PK — 내부 숙소 식별자, DB 자동 생성 IDENTITY)
- supplier
- supplier_stay_code
- stay_name
- active
- last_seen_at
- created_at
- updated_at
```

제약:

```
PRIMARY KEY(internal_stay_id)
UNIQUE(supplier, supplier_stay_code)
```

### `room_type_mapping`

```
- internal_room_type_id (PK — 내부 객실 타입 식별자, DB 자동 생성 IDENTITY)
- supplier
- supplier_stay_code
- supplier_room_type_code
- room_type_name
- max_occupancy
- active
- last_seen_at
- created_at
- updated_at
```

제약:

```
PRIMARY KEY(internal_room_type_id)
UNIQUE(supplier, supplier_stay_code, supplier_room_type_code)
```

`stay_name`, `room_type_name`, `max_occupancy`는 정적인 숙소 목록 API에서 얻어 매핑에 함께 보존합니다. 다만 이 값들은 **참고·디버깅용 스냅샷**이며, 검색 응답에 실제로 내려가는 이름·최대 수용 인원의 출처는 매핑이 아니라 검색 시점의 재고·요금 응답입니다. (아래 [의사결정](#의사결정-표시-메타데이터의-출처) 참고)

요금과 재고는 저장하지 않습니다. 검색 시점마다 값이 달라지는 동적 데이터이기 때문입니다.

### 의사결정: 표시 메타데이터의 출처

숙소명·객실 타입명·최대 수용 인원을 검색 응답에 담을 때, 그 출처를 두 가지 중에서 선택할 수 있습니다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 매핑을 출처로 | 검색 시 이름을 매핑에서 조인하므로 응답 구성이 단순 | 동기화가 실패해 매핑이 오래되면 옛 이름·인원이 노출될 수 있음 |
| 재고·요금 응답을 출처로 (채택) | 동기화가 밀려도 이름·인원이 항상 최신 | 매핑의 저장 값과 응답 값이 다를 수 있어 매핑 값은 참고용으로만 씀 |

**재고·요금 응답을 출처로 채택합니다.** 근거는 다음과 같습니다.

- 두 공급사의 재고·요금 API 응답에는 이름과 `maxOccupancy`가 모두 포함되어 있어, 매핑에 의존하지 않고도 표시 메타데이터를 구성할 수 있습니다.
- 이렇게 하면 숙소 목록 동기화가 실패해 기존 매핑으로 서비스하는 상황([5. 숙소 목록 동기화](#5-숙소-목록-동기화))에서도 이름·인원이 stale되지 않습니다. 매핑은 순수하게 `코드 → 내부 식별자` 변환에만 쓰이고, 표시 값은 항상 실시간 응답을 따릅니다.
- 재고·요금이 이미 검색 시점 실시간 값이므로, 같은 응답에서 이름·인원까지 취하면 표시 데이터의 정합성 기준이 하나로 통일됩니다.
- 매핑에 없는 신규 숙소는 애초에 조회 대상에서 빠지므로, 이 결정으로 새로 발생하는 누락은 없습니다.

## 5. 숙소 목록 동기화

숙소 목록은 검색할 때마다 조회하지 않습니다. 숙소 목록은 비교적 정적이고 재고·요금은 매번 달라지므로, 두 데이터를 같은 주기로 처리하지 않습니다.

동기화 방식은 다음과 같이 둡니다.

1. 애플리케이션 기동 시 1회 동기화
2. 설정된 주기에 따른 자동 동기화 (주기는 설정값으로 분리, 시간 단위로 충분)
3. 즉시 반영이 필요한 경우를 위한 수동 동기화 트리거

기동 시 1회만 두면 실패했을 때 복구 경로가 재시작밖에 없으므로, 주기 동기화를 정상 경로로 두어 기동 시 실패해도 다음 주기에 자동 복구되도록 합니다. 수동 트리거는 시스템이 주기적으로 하는 일을 앞당기는 보조 수단이며, 관리자 화면·권한 체계는 이번 범위 밖이므로 별도로 구현하지 않습니다.

### 동기화 실패 처리

동기화 중 한 공급사의 API가 실패하더라도 전체 애플리케이션을 종료하지 않습니다.

- 기존 매핑이 있으면 기존 매핑으로 서비스합니다.
- 기존 매핑이 없으면 해당 공급사만 검색 대상에서 제외하며, 검색 응답에는 `SKIPPED` 상태로 표기합니다. ([failure-handling.md](failure-handling.md#상태값-판정-규칙) 참고)
- 실패 내용은 경고 로그로 기록합니다.
- 복구는 다음 주기 동기화가 맡으므로 별도 재시도 로직을 두지 않습니다.

동기화 실패 시 "기존 매핑으로 서비스"가 데이터 정합성에 안전한 이유는, 재고·요금이 검색 시점 실시간 값이고 표시 메타데이터도 실시간 응답을 출처로 삼기 때문입니다. 매핑이 오래돼도 가격·재고·이름이 stale되지 않으며, stale될 수 있는 것은 "어떤 숙소를 조회 대상에 포함하는가"(신규 누락·삭제 잔존)뿐이고 이는 다음 주기 동기화에서 복구됩니다.

카탈로그(①) 장애를 재현하는 Mock 모드와 위 정책의 검증 테스트는 설계로만 남기고, 핵심 검색 흐름 완성 이후로 구현·검증을 미룹니다.

### 카탈로그에서 사라진 숙소

숙소 목록에서 더 이상 조회되지 않는 매핑은 `active` 플래그로 관리하는 것을 방향으로 둡니다. 다만 비활성화 판정 규칙의 상세와 구현은 확장 범위로 두고, 이번 구현에서는 조회된 항목의 `last_seen_at` 갱신까지만 다룹니다.
